# Clinical Programming SOP (org-clinical-programming v1.0)

This is the procedure. The TA plugin (`ta-oncology`) and study plugin (`study-onc101`) only supply parameters. The MCP server `clinical-kb` only retrieves. **You decide; the MCP retrieves.**

MCP tools (server `clinical-kb`): `get_study_context`, `search_assets`, `get_asset`, `get_counterpart`, `propose_asset`. They return code payloads only and never execute anything.

## 1. Resolve the language (stop at the first hit)

1. An explicit language in the user's request ("in SAS", "in R").
2. The language of the active editor file: `.sas` means SAS; `.R`, or `.qmd` with R chunks, means R.
3. The study default for the role: production uses `production_language`, QC uses `qc_language` (both from `get_study_context`).
4. Otherwise ask the user. **Never default silently.**

## 2. Resolve the role

The words "QC", "double program", "independently", or "verify" make it the **QC role**: follow the `clinical-qc` skill, which builds on this SOP. Anything else is **production**.

## 3. Retrieve

1. Take `study_id` from the study plugin (ONC-101 uses `study_id="ONC-101"`).
2. Call `get_study_context(study_id)`.
3. Call `search_assets(query, study_id, language=<resolved>, ta=<context.ta>, endpoint=<if identifiable, e.g. "PFS">, k=5)`.
4. If `best_score >= 0.55` **and** `hits[0].validation_status == "validated"`, call `get_asset(hits[0].asset_id, study_id)`. Otherwise, go to the **Gap procedure** (section 8).
5. Read `source_code` and `params` to understand the asset: its inputs, outputs, and required companions (for example, "Requires %censor_onc101"). Retrieve each required companion the same way. **Do not copy any of its body.**

## 4. Generate the program

- Save it under `program_root`, following `naming_convention` from `get_study_context`. For example, ONC-101 production ADTTE goes in `<program_root>/adam/adtte.sas`.
- Start with the standard header block:

```
/******************************************************************************
* Program     : adam/adtte.sas
* Study       : ONC-101
* Purpose     : <what it derives, SAP section>
* Author      : <the user>          Date: <today>
* Assets used : sas-censor-onc101-v1.0 (v1.0, validated)
*               sas-derive-pfs-v1.2   (v1.2, validated)
* Generated by: Posit Assistant (PA-GENERATED) - reviewed by <user>
******************************************************************************/
```

  For R, use the same fields as `#` comments.
- The body is: each `include_stmt` **verbatim** (companions first, for example `%censor_onc101` before `%derive_pfs`), then the call built from `call_template` with the study's dataset names and `&dcut` / `dcut`, then **glue only**: libnames, reading the input data, the cutoff variable, and saving the output. Nothing else.
- SAS: the `%include` path must be exactly the `include_stmt`. Never retype or shorten it.
- R: write `library()` and `source()` exactly as given in `include_stmt`. Never `source()` a packaged function's file.
- R reads SAS-format data with **haven** (`read_xpt`, `read_sas`) and writes XPT (`haven::write_xpt`). Never use `.rds`.

## 5. Execute

- SAS: save the program, then submit it in the SAS (Viya compute) console session with `%include "<program path>" / source2;` so the log shows the program.
- R: run it in the Positron R console (`source("<program path>", echo = TRUE)`).

## 6. Verify (all checks must pass before you report success)

- SAS log: zero `ERROR:` lines; zero `WARNING:` lines; zero `NOTE: Variable ... is uninitialized`; zero `NOTE: MERGE statement has more than one data set with repeats of BY values`. Report the observation count of the output dataset (from the `NOTE: The data set ... has N observations` line).
- R: no errors and no warnings. Report `nrow()` of the output.
- If `test_path` is present, run it. For SAS, use `%include "<test_path>";` and look for `NOTE: [TEST] <name> PASS`. For R, use `testthat::test_file("<test_path>")`. Report pass or fail.
- On failure: show the relevant log lines and propose a fix to the **glue code only**. If the failure is inside a validated asset, **stop and tell the user. Do not patch the asset.**

## 7. Report (always this shape)

| Item | Content |
|---|---|
| Assets used | asset_id, version, validation_status for each |
| Program | path |
| Execution | ran in SAS Viya / R, output dataset and N obs / nrow |
| Verification | log checks (counts of ERROR/WARNING/flagged NOTEs), test result |
| Unvalidated | anything not validated, or "none" |

## 8. Gap procedure (no validated asset)

Use this when `best_score < 0.55`, or when the top hit is not validated.

1. **Say so explicitly.** Show the nearest hits and their scores. Real example: "Derive duration of response for ONC-101" (SAS) returned `best_score 0.506` with hits `sas-derive-ttr-v1.0 0.506`, `sas-derive-bor-v1.0 0.489`, and `sas-derive-orr-v1.0 0.474`. None of these is a DoR derivation.
2. Fetch the relevant specs: `search_assets("response assessment and censoring rules", study_id, asset_type="spec", ta=...)`. This really returns `spec-recist11-response-v1.0 (0.601)` and `spec-sap-onc101-tte-v2.0 (0.414)`; read them with `get_asset`. Draft the derivation from the TA conventions and the SAP. You may still `%include` or `library()` validated building blocks (for example, the BOR and censoring assets). Draft only the missing logic.
3. Mark every generated block with `/* UNVALIDATED - PA DRAFT - requires review */` (SAS) or `# UNVALIDATED - PA DRAFT - requires review` (R). Put "UNVALIDATED" in the header's assets line as well.
4. Call `propose_asset(...)` with the draft source, `include_kind` and `include_path`, the study's reviewer, and a `rationale` that cites the scores. Report the returned draft `asset_id` (`draft-...`, version `0.1-draft`).
5. Never present a draft as validated. Never skip steps 1 and 4 and silently write the code from scratch.

## Errors from the server

Errors come back as structured objects, for example `{"error": "unknown_study", "study_id": "ONC-999", "known_studies": ["ONC-101"], ...}`. Relay them to the user; do not guess around them.

## Hard rules (repeat)

1. **Include, never inline.** Never paste a validated asset's body into a program.
2. **Never edit a validated asset.**
3. **Never invent a path.** Use `include_stmt`, `test_path`, and `program_root` exactly as the server renders them.
4. **Never translate between SAS and R.** Use `get_counterpart`.
5. **Always report what was used**: asset ids, versions, and statuses. The server logs every call.
